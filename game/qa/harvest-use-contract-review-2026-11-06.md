# 다음 개선 후보: 채소 한 그릇의 저장·소비 계약 독립 검토

2026-11-06 KST · journey_accessibility_quality · 읽기 전용 검토. 현재 배포본 runtime은 수정하지 않았다. 생활 담당의 `docs/harvest-use-next-cycle-2026-11-06.md` 설계와 협의한 결과이며, 아래 기능이 이미 구현됐다는 뜻은 아니다.

## 결론

UI는 ‘수확 한 그릇’ 한 흐름으로 묶고 내부 음식 ID는 토마토·호박·잎채소 세 변형으로 나누는 안을 권한다. 채소 1개로 한 그릇을 만들면 기존 한 번 수확의 2개로 혼자 먹을 몫과 친구 몫을 준비할 수 있다. 세 종류를 모두 모으게 하거나 계절 변경을 강제할 필요가 없다.

이것은 문자열과 메뉴만 추가하는 작업이 아니다. 고정 음식 목록의 schema 7 이행과 그릇을 준비·먹기·건네는 실제 연출이 함께 있어야 출시 가능한 최소 기능이다. 공통 음식 ID 하나에 별도 원재료 provenance 장부를 추가하는 안보다 세 고정 변형의 기존 made/consumed 장부가 단순하다.

메모리에서 기존 reducer를 읽기 전용으로 호출해 현재 계약을 별도로 확인했다. 토마토 수확 후 사용처가 없어 2개가 남고, 복숭아주스는 만들 때만 과일 2개를 쓰며 마실 때 과일을 또 빼지 않는다. 중복 준비·중복 소비·빈 주머니 소비가 거절된다. schema 6에 가상의 새 음식 키만 추가한 저장은 validator가 거절한다. 이는 새 기능 테스트나 실제 플레이 증거가 아니다.

## 최소 구현안과 불변식

1. UI 한 카드 아래에서 보유한 채소를 선택한다. 내부의 `tomatoBowl`, `pumpkinBowl`, `leafyBowl` 같은 고정 세 ID는 재료 출처이자 주머니 항목이다. 선택하지 않은 재료는 전혀 소비하지 않는다.
2. `FOOD_MEAL_IDS`와 `FOOD_PREPARED_IDS = DRINK + MEAL`처럼 실제 음식 종류를 구분한다. 그릇을 기존 DRINK 목록에 넣어 컵 동작을 억지로 재사용하지 않는다. 레시피 비용·라벨·단위·음식 종류를 하나의 고정 catalog에서 참조한다.
3. 준비 결과 받기 성공 시 선택한 made만 +1. 채소 잔량은 `harvests×2−made[variant]×cost`이며 정수·0 이상이다. cost=1 제안에서는 한번 수확으로 두 그릇이 가능하다.
4. 혼자 먹기 또는 친구에게 한 그릇 건네기의 접촉 성공 시 그 음식 consumed만 +1. 완성 음식 잔량은 made−consumed이며 0 이상이다. 이때 채소 비용을 다시 차감하지 않는다. 한 그릇을 건네면서 본인 몫까지 동시에 2개 소비하지 않는다.
5. expectedRevision + expectedMade/expectedConsumed를 시작 시 고정한다. 같은 마지막 한 그릇에 식사·공유를 동시에 준비해도 먼저 성공한 하나만 소비된다. stale action의 예상값을 자동으로 최신 값으로 바꿔 재사용하지 않는다.
6. 새 영속 ‘준비 중’/예약 카운터는 만들지 않는다. 받기 전 새로고침은 재료 그대로, 받기 후 새로고침은 음식 주머니 그대로다. 먹는 접촉 전 새로고침은 음식 그대로, 접촉 후는 정확히 하나 사용된 상태다.
7. 비용은 누적 made에서 과거 소비를 재계산하는 저장 계약이다. 출시 뒤 cost 1→2를 단순 상수 변경하면 과거 소비를 소급해 늘려 잔량 음수·저장 invalid가 생길 수 있다. 비용을 바꾸려면 별도 migration이나 새 recipe ID가 필요하다.

## schema 7에 반드시 포함할 것

- v5/v6의 과거 음식 키 목록을 고정한 validator를 따로 유지한다. 먼저 그 구조와 모든 기존 불변식을 검증한 뒤 새 made/consumed 세 키를 0으로 채운다.
- v7는 새 키 전체가 정확히 있는지 엄격히 검사한다. 구버전 형식에 새 키가 섞였거나 누락·상속·기호·비열거 키가 있으면 임의 보정하지 않는다.
- 초기 상태·validateProgress·migrateProgress의 버전 목록, save.js의 future/upgrade 판정, FOOD action의 root version guard를 함께 갱신한다. schemaVersion만 올리고 나머지를 잊지 않는다.
- 기존 SAVE_KEY/백업과 원본 보호 계약을 유지한다. 구 앱은 schema 7을 미래 버전으로 보고 쓰기를 차단해야 하며, 새 앱에서 이행 저장이 실패하면 원래 기록을 보존하고 새 소비를 막는다.
- 장식 소유권, 수확 횟수, 원래 음료·빵 누적값, revision·백업 관계를 보존한다. 1~4 버전은 기존 경로로 이행하되 새로운 음식 카운터는 0으로 시작한다.
- 음수와 NaN/Infinity/소수/초과 정수, consumed>made, 누적 제작 비용>수확 재료를 거절한다. 파일 상한 32768자도 기존대로 유지한다.

## 취소·실패·재접속의 통과 조건

| 지점 | 취소/장면 전환/재접속 결과 |
| --- | --- |
| 재료 고르기·준비 애니메이션·받기 전 | 재료와 음식 수량 모두 그대로. 늦게 끝난 비동기 준비는 폐기 |
| 받기 저장 실패 | 재료 그대로, 새 음식 없음. 실패 원인과 다시 받기 제공 |
| 받기 저장 성공 뒤 | 재료 1 차감·음식 1 증가 유지. 창 닫기가 환불을 만들지 않음 |
| 혼자/친구 접촉 전 | 완성 음식 그대로. 좌석·친구 토큰이 달라지면 소비 금지 |
| 소비 저장 실패 | 음식 그대로. 이미 먹었다는 화면·친구 반응을 확정하지 않음 |
| 소비 저장 성공 뒤 | 완성 음식 정확히 1 감소 유지. 다시 탭하거나 돌아와도 같은 접촉 재실행 금지 |
| 다른 탭·구버전·저장 충돌 | 읽기 전용/기록 보호를 우회하지 않음. 실패를 성공 반응으로 표현하지 않음 |

저장 공간 부족으로 revision이 그대로인 실패는 같은 의도로 재시도할 수 있다. 다른 정상 거래로 revision이 바뀌었다면 과거 action이 유효해지는 것은 아니므로 다시 선택하게 해야 한다. ‘저장 실패’ 버튼을 무한히 누르게 하지 않도록 상태 변경/충돌과 단순 저장 실패를 구분해 안내하는 것이 좋다.

## 실제 배움과 다시 할 이유

단순히 숫자 1을 빼고 칭찬만 보여 주면 반복 가치는 낮다. 토마토·호박은 열매, 잎채소는 잎이라는 기존 관찰을 준비 전 모양과 접시에 놓인 재료에 연결한다. 색·형태·잘라 놓은 모습이 실제로 달라지고, 친구가 그 차이를 짧게 언급하도록 한다. ‘오늘은 어떤 색의 한 그릇을 나눌까’ 정도의 선택이면 된다.

조리법·영양 효과를 검증하지 않은 채 건강 효능이나 과학 학습 성과를 주장하지 않는다. 칼질이나 가열을 보여 주면 실제 애니메이션과 설명이 맞아야 하며, 하지 않은 조리를 대사만으로 완료했다고 하지 않는다. 연속 방문 보상·3종 수집 의무·점수 경쟁을 붙이지 않아도 음식주머니에 남은 한 몫을 다음 방문 때 나누는 사용 이유가 생긴다.

구현 완료 판단에는 최소 한 그릇의 준비→받기→본인 식사, 다른 한 그릇의 친구 초대→공유, 반복 수확→두 번째 준비, 세 재료 차이, 네 취소/재접속 경계, 저장 거절·중복 탭·동시 마지막 수량, 기존 v5/v6 저장 이행을 포함해야 한다. 폰 가로에서도 재료 선택과 나가기·받기·재시도가 읽히고 닿아야 한다. 현재 배포는 이 후속 후보 때문에 바꾸지 않는다.

## 최종 계획 문서 대조

생활 담당의 `docs/harvest-use-next-cycle-2026-11-06.md` 초안 전체를 읽고 위 계약과 대조했다. 고정 3 variant·새 카운터 6개·cost 1·과거 키 검증 뒤 이행·단일 입 접촉 소비·취소/재접속·backupRaw 실패 재시도가 모두 반영되어 있다. 다음 주기 설계로 진행 가능한 상태이며 차단 지적은 없다. 새 조작부는 기존 48px 기준으로 통일하고, ‘익힌 채소’ 설명은 최종 3D 준비 상태가 실제로 뒷받침하도록 확인하라는 두 문구 권고를 전달했다. 아직 구현이나 새 음식 완주를 검증한 것은 아니다.
