## 확인된 문서 문제와 통합 확인 후보

### 해결됨 · 현재 테스트 수 문서 불일치 (초기 P2 문서 지적)

`README.md:17`은 현재 41개 파일/198개 검사라고 쓰고, 같은 문서의 2026-10-25 절은 현재 193개라고 쓴다. 새 회귀가 추가된 이번 출시의 현재 수치와 일치하지 않는다. 사용자가 검증 범위를 오해할 수 있으므로 최종 실행 후 현재 수치를 한 곳에서 관리하거나 최신 출시 기록으로 연결하고, 과거 수치는 당시 결과로 표시한다. 통합 담당자에게 전달했고 후속 소스에서 현재 수치 대신 최신 출시 기록을 참조하며 193개는 당시 결과로 바뀐 것을 확인했다. 현재 미해결 사항으로 남기지 않는다.

### 소스상 해소 · 고정 높이 음악실과 공통 footer

`dist/ui.js:100`의 `workshop()`은 모든 kind에 `.workshop-return`을 추가한다. `dist/style.css:115`의 `music-workshop`은 dialog 높이가 viewport에 고정되고 overflow가 숨겨져 있으며, 내부 flex 레이아웃의 music-stage는 최소 150px이다. 제목·조작 패널·새 footer가 함께 놓이는 휴대폰 가로 844×390에서 아래쪽 조작/복귀를 가리는지 최종 실제 브라우저로 확인할 필요가 있다. 기존 X가 남으므로 소스만으로 잠김/P1이라고 확정하지 않았다. 확인되면 footer를 스크롤 가능한 panel 안에 넣거나 고정 장면 kind에서 별도 적용하는 방식이 적절하다. 중복 브라우저를 실행하지 않고 root의 최종 검증에 추가 요청했다. 후속 `ui.workshop`은 `returnButton` 옵션을 추가하고 실제 호출 kind인 `music-workshop`과 `throw-workshop`에서는 기본값을 false로 둔다. 두 컨트롤러의 실제 kind와 기존 상단 나가기 버튼을 대조했으며 footer 때문에 공간이 늘어나는 후보는 소스상 해소됐다. 별도로 발견된 음악실 파스텔 CSS/가로 배치 회귀의 수정·브라우저 결과는 최종 검증을 따른다.

최종 제품 변경 이후 `npm run check`, 전체 `npm test`, 새 로드의 module/CSS 404·pageerror 없음, 폰/태블릿/데스크톱의 실제 완료·닫기·재시도·저장/복구 결과가 필요하다. 위 미확정 후보가 P0/P1로 확인되면 수정/재검증 전에는 배포하면 안 된다. GitHub commit과 Vercel 공개 commit/version, OG/아이콘 HTTP 응답을 대조해야 한다. 도름스의 교사 인증·게시 완료는 별도이며, 세션 부재를 배포 성공으로 대체하지 않는다.

실물 모바일 GPU, iOS Safari, 실제 터치 하드웨어, 음성 청취 품질, 실제 사용자의 장기 재미/학습 효과는 이 리뷰에서 검증하지 않았다. Chromium의 viewport/touch 에뮬레이션과 소프트웨어 WebGL을 실물 기기 시험으로 표현하지 않는다.


## 마지막 통합 변경 재검토

- 뜰채 잡기는 pointerdown의 button=0을 사용하므로 두 번째 손가락(isPrimary=false)도 조작할 수 있다. preventDefault 뒤 포인터 합성 click(detail>0)은 무시하고 키보드/보조기술 click(detail=0)은 유지한다. 잡기만 이동키/스틱을 지우지 않으며 모형은 뜰채 동작 중 이동을 멈춘다. 따라서 동작 후 첫 손가락을 다시 떼지 않아도 이어 움직이고, 일시정지·종료는 계속 입력을 초기화한다. 이벤트는 세션 cleanup 목록으로 제거한다. 관련 회귀가 이 계약을 직접 확인한다.
- 작은 폰의 뜰채 패널은 두 열 버튼, 짧은 터치 안내, 준비/결과별 불필요한 설명 숨김을 적용한다. 헤더는 오른쪽 닫기 자리를 padding으로 확보한다. 실제 두 손가락·최종 패널 가독성은 담당자의 브라우저 증거를 따른다.
- 코스터의 상단 activity-note가 하단 공간으로 잘못 계산되어 화면을 극단적으로 줄이던 P1은 root의 deep QA에서 발견됐다. 현재 `coasterSafeArea`는 stage 상대 좌표로 실제 하단/오른쪽 패널만 분류하고 top≤25%, bottom≤42% (가로≤25%), 오른쪽≤46%로 제한한다. 기존 고정 전체 모델/카메라 소유권을 바꾸지 않는다. 회귀는 오프셋 불변성, 상단 안내 유무, 작은 화면 면적, 원본 도름이의 루프 중 화면 내 위치와 48px 최소 크기를 확인한다. 소스상 수정이 문제 원인에 맞으며 root에게 전달된 코스터 폰 화면 복구 결과와 결합해 판정한다.
- 범퍼카/카트도 상단 안내를 하단 경계로 사용하지 않고 유효 장면 면적을 남긴다. 카트의 추가 하단 상태 공간은 48%로 제한되며 top 최대25%와 합쳐 화면이 0으로 줄지 않는다. 기존 모델/관절 자산의 스케일을 바꾸지 않는다.
- 도서관의 실제 접근 범위 .56, 표시 원 .50은 동일한 표적 중심을 사용한다. 현재 표적 재검증 및 가까운 표적 정렬을 유지해 임의 원격 상호작용을 허용하지 않는다.

이 마지막 변경의 소스 검토에서 새 확정 P0/P1/P2 제품 결함은 발견하지 않았다. 최종 npm 전체 실행과 음악실 CSS 수정·뜰채 두 손가락 브라우저 증거가 완료될 때까지 조건부 판정을 유지한다.

최신 `dist/release.css`의 변경도 읽었다. 공통 파스텔 dialog 배경 선택자에서 `music-workshop`과 `throw-workshop`을 제외하고, 두 live-world stage의 투명 배경/그림자 없음 계약을 명시적으로 복원한다. 낮은 가로 화면(폭≥621, 높이≤520)에서 음악실을 좌우로 배치하고 stage의 min-width/min-height를 0으로 두며, 조작 panel은 너비60%와 자체 스크롤을 사용한다. 피아노의 선택/버튼 행과 건반 높이, 현악기 버튼/도구바를 이 범위에만 조정한다. 기존 modal X, 네이티브 선택, 연주 이벤트 소유권·음성 cleanup은 바꾸지 않는다. 현재 코드에서 새 확정 P0/P1/P2를 찾지 못했다. 이 판정은 최종 가로 화면에서 실제 악기·조작·나가기를 확인한 브라우저 결과와 결합해야 한다.

## 일반 테마·워크숍 footer 근본 수정 최종 검토

후속 체육관 검수에서 음악 외의 live-world dialog에도 크림 배경 가림이 발견되어, root가 바꾼 최신 `dist/release.css`와 `dist/ui.js`를 다시 독립 검토했다. **두 파일의 수정 사양·코드 품질 PASS, 새 확정 P0/P1 없음.** 이 절이 앞선 음악/던지기 예외와 footer 범위 설명보다 최신이다.

`dialog:where(:not(.village-map))`는 :where 안쪽의 class를 specificity에 더하지 않아 일반 dialog 수준(0,0,1)의 테마가 된다. 따라서 먼저 로드된 `dialog.gym-workshop` 등 전용 class 규칙(0,1,1)이 배경·border·shadow를 계속 결정한다. 이는 개별 활동 이름을 빠뜨릴 수 있는 제외 목록보다 근본 원인에 맞는 수정이다. 마을 지도는 일반 테마 대상에서 계속 제외하고, music/throw의 투명 규칙도 유지한다. 일반 school-workshop은 기존 dialog 배경보다 뒤의 기본 크림 테마를 사용한다.

`workshop()`의 기본 `returnButton`은 이제 `kind==='school-workshop'`인 경우에만 true다. 실제 gym의 복합 kind(`gym-workshop climbing-workshop` 등), music/throw 및 다른 전용 화면에 추가 footer를 넣지 않으므로 고정 높이/라이브 장면 레이아웃 계약을 침범하지 않는다. 기존 첫 번째 상단 닫기 버튼과 closeLabel, cleanup 및 모달 close→unlock 계약은 모든 kind에서 그대로 생성된다. 이야기/지도처럼 school-workshop에 추가 class가 있는 화면도 기본 footer를 받지 않지만 상단 sticky 닫기 경로는 유지한다. 필요하면 호출자가 명시적으로 returnButton=true를 선택할 수 있다.

`verify-dialog-surfaces.mjs`는 실제 index의 CSS 로드 순서를 가져와 Chromium computed background/shadow를 10종에서 비교하므로 이 specificity 회귀를 검증하기에 맞다. 단순 mock/style 문자열 검사와 다르다. 다만 이를 실제 도름이·체육기구 렌더나 완료 조작 증거로 확대할 수는 없다. 체육7종의 새 브라우저 결과는 별도 보고서를 따른다.
